# oojam: guide for the daily builder

oojam.dev is a website with no designated purpose. Every day the community votes for one
idea at build.oojam.dev, and you build it here. Your work is checked from outside this
repository by automated guardrails, an independent Claude review, and a browser smoke test.
Breaking any rule below fails the build, so follow them exactly.

**Build exactly one idea per run: the one in your task.** Don't fix, refactor or restyle
unrelated things. If your task includes a gate report from a previous attempt, fix every
blocking finding in it first.

## Stack and layout

React Router v7 (framework mode, server-rendered), React 19, TypeScript (strict), Tailwind
CSS v4, Drizzle ORM on Postgres 17 (`postgres` driver), Vitest. Node 22. `~/` imports from `app/`.

| Path | What goes there |
|---|---|
| `app/routes.ts` | Every route, registered explicitly: `route("guestbook", "routes/guestbook.tsx")`. |
| `app/routes/*.tsx` | Pages: `default` component, plus `loader`, `action`, `meta` as needed. Types come from `import type { Route } from "./+types/<file>"` (generated by `npm run check`). |
| `app/routes/*.ts` | Resource routes (no default export) for JSON or other non-HTML responses. |
| `app/components/` | Shared React components. |
| `app/lib/*.ts` | Logic. Name server-only modules `*.server.ts` (database, `node:*`, secrets of any kind) and never import them from components. |
| `app/db/schema.ts` | Drizzle schema. `getDb()` in `app/db/client.server.ts` gives you the client. |
| `drizzle/` | Generated migrations. Never edit by hand (see Database). |
| `app/app.css` | Tailwind and the design tokens. |
| `public/` | Static files served from `/`. |
| `content/builds.json` | The changelog. Written by the platform only. |

Patterns:
- Read data in `loader`, change it in `action`. Use `<Form method="post">` (or `useFetcher`).
  Validate every input on the server, and return errors with `data({ error }, { status: 400 })`.
- Each new feature gets its own route, linked from the home page (`app/routes/home.tsx`).
  Add the link above the changelog. The changelog section must stay as it is.
- Design: use the tokens `bg-paper`, `bg-panel`, `text-ink`, `text-muted`, `border-line`,
  `text-jam`, `bg-jam`, `bg-jam-soft`. They switch automatically for dark mode
  (`prefers-color-scheme`). Use system fonts only. Pages must work from 320 px wide, use
  semantic HTML, label every control, keep visible focus, and meet WCAG AA contrast.
- The filesystem is read-only at runtime (only `/tmp` is writable, and it's wiped on every
  deploy). Anything that must persist goes in Postgres.

## Database

The site runs as a role that can only `SELECT`, `INSERT`, `UPDATE` and `DELETE`. Migrations
are applied by the deployer before release. There's no database in your build environment,
so don't try to run `db:migrate`; the smoke test applies your migration to a copy of
production data.

To change the schema:
1. Edit `app/db/schema.ts`.
2. Run `npm run db:generate`. It writes `drizzle/NNNN_<name>.sql` and updates `drizzle/meta/`.
   Keep both. For seed rows, `npm run db:generate -- --custom --name <name>` creates an empty
   migration for you to fill with `INSERT` statements.
3. Read the generated SQL. It must contain only allowed statements.

**Migrations are additive only.** Never edit, rename or delete an existing migration,
snapshot or journal entry.

| Allowed | Blocked |
|---|---|
| `CREATE TABLE`, `CREATE [UNIQUE] INDEX`, `CREATE SEQUENCE`, `CREATE TYPE ... AS ENUM`, `CREATE VIEW` | `DROP` anything, `TRUNCATE`, `DELETE` |
| `ALTER TABLE ... ADD COLUMN`, `ADD CONSTRAINT`, `ALTER COLUMN ... SET DEFAULT`, `DROP DEFAULT`, `DROP NOT NULL` | `ALTER COLUMN ... TYPE`, `SET NOT NULL`, any `RENAME` |
| `ALTER TYPE ... ADD VALUE` | `GRANT`/`REVOKE`, roles, extensions, `DO` blocks |
| `INSERT`; `UPDATE ... WHERE ...` | `UPDATE` without `WHERE`; `CREATE FUNCTION/PROCEDURE/TRIGGER/RULE`; `COPY`; `SET ROLE`/`SET SESSION`; `ALTER SYSTEM` |

So in `schema.ts`:
- Never remove, rename or change the type of an existing table or column. drizzle-kit would
  generate a `DROP` or `RENAME` and the build fails. If a column is no longer needed, leave it.
- New columns on existing tables must be nullable or have a default.
- Prefer `bigserial` ids and `timestamp(..., { withTimezone: true }).defaultNow()`.

The database also refuses, at runtime: dropping objects, `TRUNCATE`, deleting more than 500
rows in one statement, and statements over 30 s. Pages must work both on empty tables and on
real data. Use Drizzle's query builder; don't use `sql.raw()` or `.unsafe()`.

## Hard rules

1. **Protected paths.** Don't create, modify, delete or rename: `.github/**`, `LICENSE`,
   `CLAUDE.md`, `Dockerfile`, `.dockerignore`, `.npmrc`, `.nvmrc`, `.oojam/**`,
   `scripts/migrate.mjs`, `app/routes/_health.ts`, `app/lib/oojam-identity.server.ts`,
   `app/routes/_oojam.callback.ts`, `app/routes/_oojam.signout.ts`, `content/builds.json`,
   `.claude/**`, `.mcp.json`, `.gitattributes`, `.gitmodules`, `.git/**`, and existing
   `drizzle/*.sql` or `drizzle/meta/*_snapshot.json` files. You may add routes to
   `app/routes.ts`, but keep its three managed lines (`_health`, `_oojam/callback`,
   `_oojam/signout`) exactly as they are. No symlinks, no files over 1 MB, no binary files
   outside `public/`, at most 200 changed files.
2. **Dependencies.** Prefer none: the platform and React cover most needs. If you must add one:
   at most 5 new direct dependencies, each pinned to an exact version (`npm install --save-exact`),
   published at least 14 days ago, not deprecated, from registry.npmjs.org, and without
   install scripts. Don't change the `start`, `build`, `check`, `test`, `db:migrate` or
   `db:generate` scripts, and don't add lifecycle scripts (`preinstall`, `install`,
   `postinstall`, `prepare`, `prepublish`, `prepack`, `postpack`).
3. **Environment.** Read only `process.env.DATABASE_URL`, `PORT`, `NODE_ENV` and `GIT_SHA`.
   There are no other settings or secrets, and you can't add any.
4. **No network.** The site has no internet access. No outbound `fetch` or HTTP calls, and no
   third-party scripts, fonts, images, iframes, analytics or embeds. The edge CSP
   (`default-src 'self'`) blocks them anyway. Inline scripts and styles, and `data:`/`blob:`
   images, are fine. Plain links to other sites are fine.
5. **Unsafe code.** No `eval`, `new Function`, `child_process`, `vm`, `process.binding`, or
   writing files. No `dangerouslySetInnerHTML` or `innerHTML`. Use `node:crypto` for anything
   random that matters (never `Math.random()` for ids or tokens). Nothing secret in
   `localStorage`.
6. **Content policy.** Don't build anything involving: illegal, sexual or hateful content,
   harassment, or real private individuals; malware, mining, tracking, fingerprinting or ads;
   collecting personal data beyond what the feature strictly needs (never passwords, payment
   details or government IDs, and no email addresses without a clear purpose); taking payments;
   impersonating a real person, brand or organisation; or changing oojam's guardrails, voting,
   payments, licence, CI or deploy configuration. Never build your own accounts, passwords or
   logins: identity comes only from "Sign in with oojam" (see Identity below).
7. **User-generated content.** Anything visitors submit that others can see must:
   - pass through `cleanText(input, maxLen)` from `~/lib/ugc.server` before it's stored, with a
     sensible length limit, and reject empty results;
   - be rate-limited per IP with `createRateLimiter` and `enforceRateLimit` from
     `~/lib/rate-limit.server`;
   - be rendered as plain text through React (`{item.body}`), never as HTML or Markdown-to-HTML;
   - have a report button that hides the item after 3 reports from different visitors. Follow
     the report-to-hide pattern documented at the top of `app/lib/ugc.server.ts`. Store
     `reporterKey(request)`, never raw IP addresses.

   **Uploads need a signed-in GitHub user.** Anything visitors upload (images, audio, video or
   any file) requires `requireViewer(request)`. Store the uploader's `githubId` and `login`
   with the item, show "@login" (linked to `https://github.com/<login>`) wherever it appears,
   and rate-limit by `githubId` as well as by IP. Signed-out visitors see the item list and a
   "Sign in with GitHub to post" link (`signInUrl(path)`), never the upload form. Text
   submissions may stay anonymous, but attribute them when the visitor is signed in.
8. **Preserve what others built.** Other people voted for every existing feature. Integrate
   with them; don't replace, remove or break them. Changing how something looks is fine.
   Don't delete routes, tables, columns or data. Don't edit `content/builds.json`.
9. **Don't touch git.** Don't commit, push, or change git config. The platform commits your work.

## Identity

Visitors can sign in with GitHub through build.oojam.dev ("Sign in with oojam"). Use only these,
from `~/lib/oojam-identity.server`:

- `getViewer(request)` returns `{ githubId, login }` or `null`. Use it in loaders and actions.
- `requireViewer(request)` returns the viewer, or redirects them to sign in and come back.
- `signInUrl(path)` is the href for a "Sign in with GitHub" link that returns to `path`.
- Sign-out is a link or form to `/_oojam/signout?return=<path>`.

Key anything you store by `githubId`, which is stable; logins can change. Never take a username
from a form, header or URL. The site can't show GitHub avatars, because the CSP blocks other
hosts, so show "@login" instead.

## Smoke test

The gate starts the built image against a copy of production data and loads `/` plus the
routes you list in a real browser. It fails on any HTTP status of 500 or above, any console
error, any failed request (a missing asset counts), any CSP violation, and any request to
another host. Every route you list must load with a plain GET, with no prior setup and nobody
signed in. Pages that need sign-in should show a sign-in prompt to signed-out visitors, not an
error.

## Before you finish

1. Write Vitest tests for new logic, as `*.test.ts` next to the code. Keep database code thin
   and test the logic around it. Don't delete or skip existing tests.
2. Run `npm run check && npm test && npm run build`. All three must pass.
3. Reply with a short summary of what changed (features, files, any migration), then a final
   line listing up to 5 routes to smoke test, for example:

   `ROUTES: /guestbook, /guestbook/about`

If the idea can't be built within these rules, stop and reply starting with `GAVE_UP:` and
the reason, for example `GAVE_UP: needs a third-party map service, and the site has no
network access.` Don't build a partial or rule-breaking version.
